# Security

Security requirements and implementation decisions for the CLS project.

---

## Overview

The system has three user roles (admin, cleaner, customer) and several unauthenticated access patterns (public website, token-gated views). Security is enforced at multiple layers.

---

## Security Layers

```
Request
  │
  ├─ 1. Next.js Middleware (route guards, session refresh)
  │
  ├─ 2. Server Actions (session verification + role check before every mutation)
  │
  ├─ 3. Supabase RLS (database-level enforcement — final defense)
  │
  └─ 4. Storage Policies (bucket-level access control)
```

---

## Authentication

- **Provider:** Supabase Auth (email + password)
- **Session storage:** HTTP-only cookies via `@supabase/ssr`
- **Session refresh:** Middleware refreshes expired tokens on every request
- **Password reset:** Supabase built-in email reset flow

### Admin Accounts

- Created manually by the company (Supabase dashboard or admin invite)
- Optional MFA via Supabase Auth (post-MVP)

### Cleaner Accounts

- Created by admin via `/dashboard/cleaners/new`
- System auto-generates a strong password (12+ chars, mixed case, numbers, symbols)
- Admin copies credentials and sends via WhatsApp manually
- Cleaner logs in at `/auth/v2/login`

### Customer Accounts

- Customers do not need accounts in MVP
- Booking submission is anonymous (email + name only)
- Quote acceptance and invoice viewing are via token links (no auth required)
- Customer portal (login to view booking history) is a post-MVP feature

## Route Security

### Middleware Route Guards

```
/dashboard/*  → requires session + role = 'admin'
/cleaner/*    → requires session + role = 'cleaner'
/auth/*       → allow (redirect to dashboard if already logged in)
/q/*          → allow (token validated by DB lookup)
/i/*          → allow (token validated by DB lookup)
/jobs/*       → allow if logged in as cleaner, else redirect to login
/*            → allow (public website)
```

### Unauthorized Handling

- Wrong role accessing a protected route → redirect to `/unauthorized`
- Unauthenticated accessing protected route → redirect to `/auth/v2/login?next=[original URL]`
- Cleaner accessing another cleaner's job via token → 404 (RLS returns nothing)

## Token-Gated Access

Three types of public token links exist:

| Token Type | Table | Column | Purpose |
|---|---|---|---|
| Quote token | `quotes` | `token` (UUID) | Customer views/accepts quote |
| Invoice token | `invoices` | `token` (UUID) | Customer views invoice |
| Job token | `jobs` | `secure_token` (UUID) | Cleaner receives assigned job link |

### Token Security Properties

- UUIDs generated by `gen_random_uuid()` (cryptographically random)
- Not guessable (128-bit entropy)
- Stored in database — validated by lookup, not JWT
- Quote token: respects expiry date; expired quotes show "Quote Expired" page
- Job token: validated against `jobs.cleaner_id = auth.uid()` after login

### Token Expiry (MVP)

- Quote tokens: expire when `quotes.expiry_date` passes
- Invoice tokens: no expiry (customer should always be able to view their invoice)
- Job tokens: no expiry in MVP (post-MVP: expire after job is completed or N days)

## Row Level Security (RLS)

All tables have RLS enabled. See `docs/database-schema.md` for full policies.

### Key Rules

| Role | Can See |
|---|---|
| Admin | Everything |
| Cleaner | Only their own assigned jobs + related photos |
| Customer (authenticated) | Only their own bookings, quotes, invoices |
| Anonymous | Nothing (except via Server Actions with token lookup) |

### Critical: Cleaner Job Isolation

A cleaner must never be able to see another cleaner's job. This is enforced at two levels:

1. **RLS:** `jobs.cleaner_id = auth.uid()`
2. **Application:** Secure token lookup verifies `cleaner_id` matches session user before redirecting

## File Upload Security

- All uploads go through Supabase Storage (never directly to disk)
- Accepted file types: JPG, PNG, HEIC
- Maximum file size: 10MB per file, 50MB per booking (configurable via settings)
- Files compressed client-side before upload (reduces storage and bandwidth)
- Storage paths use booking/job UUIDs (not user-provided names) to prevent path traversal
- MIME type validated server-side (Supabase Storage policy)

### Storage Path Format

```
booking-photos/{booking_id}/{uuid}.{ext}
job-photos/{booking_id}/{before|after}/{uuid}.{ext}
```

---

## Input Validation

- All form inputs validated with Zod schemas before server action execution
- No raw SQL — all DB access via Supabase client (parameterized queries)
- HTML output escaped by React (XSS protection built-in)
- Admin notes and customer notes are plain text (no HTML/markdown rendering in MVP)

---

## GDPR Compliance

- Booking form includes a consent notice for photo uploads
- Customer email stored and used only for booking communications
- No third-party analytics on customer-facing pages (only Vercel Analytics on admin portal)
- Data retention policy: defined in Open Decisions (post-MVP)
- Customers can request data deletion via support contact (manual process in MVP)

---

## Error Handling & Logging

- All server actions wrapped in try/catch
- Errors logged server-side (console in dev, Supabase log drain in production)
- User-facing error messages never expose internal details
- Error boundaries on all page components
- Supabase error codes mapped to user-friendly messages

---

## Open Security Decisions (Post-MVP)

- MFA for admin accounts
- Rate limiting on booking form submission (prevent spam)
- Rate limiting on login attempts (Supabase Auth handles basic protection)
- Job token expiry after completion
- Photo retention policy (how long to keep before/after photos)
- GDPR: customer data deletion workflow
- CSP headers configuration
- Penetration testing before production launch
